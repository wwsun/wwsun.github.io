> [!note] 核心结论
> 应对企业级复杂代码库，纯粹的 Vibe Coding 极易导致上下文漂移与幻觉扩散。**REPIT 框架（Research → Propose → Plan → Implement → Test）** 将迭代拆分为五步确定性门禁：**前期（调研/提议/规划）重兵投入顶级推理模型与人类审核，后序（实现/测试）基于纯净上下文与轻量模型极速交付**，用工程流程锁死 Agent 的可靠性。可与 [[anatomy-of-coding-agent-harness]] 及 [[context-tax-and-compaction-timing]] 关联阅读。

## 核心要点与机制

### 1. REPIT 五步闭环与分层路由矩阵

| 阶段                     | 核心任务与工件产出                                    | 核心 Prompt 约束                                             | 推荐模型档次                      |
| :----------------------- | :---------------------------------------------------- | :----------------------------------------------------------- | :-------------------------------- |
| **1. Research（调研）**  | 提炼代码拓扑与现状契约；产出 `research.md`。          | **铁律：只记录现状，严禁提出任何改进方案**，防止发散污染。   | 顶级推理模型（高长文本理解）      |
| **2. Propose（提议）**   | 针对诉求给出 **2 个截然不同**的候选方案，供人类裁决。 | 强制博弈对比（如最小化改动 vs 扩展性重构），禁止单方案偏见。 | 顶级推理模型（高发散权衡）        |
| **3. Plan（规划）**      | 细化选中方案；产出包含 Out of Scope 的 `plan.md`。    | **必须显式声明“坚决不做的事项”**，扼杀自主过度工程化。       | 顶级推理模型（高精度规范）        |
| **4. Implement（实现）** | 基于纯净上下文，逐步消费 `plan.md` 实施代码修改。     | **极简指令驱动**（如 `"请严格依据 plan.md 落实修改"`）。     | 轻量/快速代码模型（低成本高吞吐） |
| **5. Test（验证）**      | 黑盒验证行为契约，捕获测试运行日志完成自检。          | 必须亲自调用终端执行测试套件，拿真实执行凭据交付。           | 轻量/快速模型                     |

### 2. 关键工程机制

- **为什么 Propose 强制固定为 2 个方案？**：单个方案容易陷入模型的初始概率陷阱；3 个以上方案边际收益显著递减且过度消耗人类审阅心智。强制 2 个方案能以最低认知负载覆盖最核心的架构权衡。
- **Out of Scope 的防御价值**：整份计划中价值最高的章节并非“做什么”，而是明确定义“本次绝对不做的事项”，直接掐断 Agent 盲目扩展依赖与引入多余抽象的冲动。

## 实践启示 / 落地规则

1. **上下文清洗时刻（Context Refresh）**：从 Propose 进入 Implement 时，**必须从上下文中彻底清除被否决的备选方案**，仅挂载最终选定的 `plan.md` 工件启动干净会话。历史残留的未采用方案是诱发实现期幻觉的头号污染源。
2. **警惕“有效 Token”错觉**：百万级大窗口中通常只有 30%–50% 是推动决策的有效 Token。坚决通过 Research 阶段的信息压缩保留高密度上下文，而非盲目硬塞整个代码仓库。
3. **复杂度动态分流**：单行修复、配置微调等轻量任务直接单轮对话驱动，避免过度流程化；凡涉及跨模块修改、新增特性或架构重构，严格执行五步闭环门禁。
