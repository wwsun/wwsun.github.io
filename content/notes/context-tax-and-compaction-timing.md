> [!note] 核心结论
> 基于 LangWatch 对 2,451 个会话、28.7 万次 API 调用的遥测实证：放任 Agent 上下文滑向百万级存在巨大的**「上下文税（Context Tax）」**（上下文尺寸每翻倍，累积消耗 Token 增长约 6 倍）。但盲目频繁压缩又会引发**「后压缩迷雾（Post-Compaction Fog）」**（人类纠错率暴增 2.37 倍）。工程黄金压缩窗口应落在 **250k 到 450k tokens**，并辅以「摘要历史 + 原生上下文尾巴（Verbatim Tail）」渐进架构。可与 [[anatomy-of-coding-agent-harness]] 及 [[claude-code-plan-mode]] 关联阅读。

## 核心要点与机制

### 1. 为什么 Prompt Cache 掩盖了巨大的成本？

在包含多步工具调用（读写文件、跑单测、查 Git）的 Agent 循环中，**每一步工具调用都会将全部累积上下文全量重发给模型**（例如 25 步 × 500k = 1,250 万 Token 调用量）。哪怕命中缓存享受低单价，高频步数乘积依然会导致计费限额瞬间击穿；而在此期间，模型有效推理能力的增量却几乎停滞。

### 2. 压缩的双刃剑：后压缩迷雾（Post-Compaction Fog）

过度激进的压缩会直接损伤智能体表现：

- **人类纠错率飙升**：传统压缩往往切除 99% 的原始细节（将 570k 压缩为 4k 摘要）。压缩后前 5 步内，人类用户的介入纠错率从基线 17.7% 骤升至 **41.9%（2.37 倍）**，且这种认知失真状态会延续约 30 步。
- **低阈值死循环**：若将压缩阈值设得过低（如低于 200k），Agent 刚走出迷雾便会再次触发压缩，导致生命周期全盘陷入“失忆与摸索”。

### 3. 分场景最佳压缩阈值推荐矩阵

| 研发任务类型           | 推荐压缩阈值    | 核心决策依据                                                                       |
| :--------------------- | :-------------- | :--------------------------------------------------------------------------------- |
| **PR 审查与推进**      | **200k ~ 250k** | 原生文本强依赖度极低（约 2%），摘要足以支撑代码合规判断，尽早压缩控成本。          |
| **技术调研与方案探索** | **250k ~ 300k** | 探索过程相对独立，阶段性结论一旦提炼，早期海量搜索排障文本可安全丢弃。             |
| **QA 测试与联调**      | **250k ~ 350k** | 测试日志衰减极快，仅需保留断言与报错上下文。                                       |
| **核心业务与功能构建** | **300k ~ 450k** | **原生文本依赖最高**。代码精细重构与字符串替换对上下文细节极敏感，需要更长清醒期。 |
| **复杂系统理解**       | **300k ~ 450k** | 依赖拓扑缓慢累积，过早压缩会导致 Agent 反复重新检索相同文件。                      |

## 实践启示 / 工程方案

1. **保留“原生上下文尾巴”（Verbatim Tail）**：淘汰“切除 99% 历史直接改纯文本摘要”的激进做法；采用“远期对话摘要化 + 保留近期 30k–60k 原生对话细节”的折中策略，平滑过渡迷雾期。
2. **严控子代理（Subagent）继承负担**：避免派生继承父级完整 500k 上下文的长寿命 Worker。子代理任务必须原子化、短寿命，冷启动并在任务完成后立即销毁。
3. **重型操作前主动执行清理**：在启动大型测试套件或全局 Lint 之前，主动执行一次 `/compact`，避免携带几十万上下文连续执行数十条无谓命令。
4. **锚定 350k 心理预警线**：在日常业务开发中，以 350k 为预警线，在 400k 左右达成当前里程碑并触发压缩，兼顾逻辑清醒度与算力经济性。
